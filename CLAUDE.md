## Dossier — the active project

### Load-bearing thesis
HMLR's `DossierStorage` (compiled, cross-topic state) and Karpathy's wiki pages (compiled, entity-indexed markdown) are the same abstraction applied to different input streams. Dossier swaps HMLR's SQL-blob output for markdown files in `wiki/` and keeps everything else — Governor-style routing, FactScrubber, Gardener, temporal supersession — intact.

### Commands
All commands run from `dossier/`.

```bash
# install (editable, with dev deps)
pip install -e ".[dev]"

# run the CLI
python -m dossier ingest raw/some_article.md
python -m dossier query "what did Alice say about vegetarianism?"
python -m dossier gardener          # consolidation + lint pass
python -m dossier chat              # interactive dialogue (HMLR-backed)

# tests
pytest                              # all
pytest tests/test_governor.py       # one file
pytest -k test_routes_document      # one test by substring
pytest -x --ff                      # fail-fast, failed-first
```

HMLR itself is an **optional runtime dependency**. If it's installed (`pip install hmlr` or from source) the full dialogue pipeline engages; if not, `dossier.hmlr_adapter` falls back to a stub so the document-ingest and wiki paths still work for testing. This is deliberate — the MVP's §10 spike needs to run before committing to HMLR as a hard dep.

### Architecture

```
dossier/
├── raw/            # immutable source documents (Karpathy layer 1)
├── wiki/           # LLM-maintained markdown (Karpathy layer 2, = HMLR dossiers)
│   ├── index.md    # content catalog, regenerated by Gardener
│   ├── log.md      # append-only activity log
│   ├── entities/   # one page per person/org/thing
│   ├── concepts/   # one page per idea/policy/constraint
│   └── sources/    # one summary page per raw/ source
├── .hmlr/          # engine internals (SQL fact store, bridge blocks, embeddings)
├── src/dossier/    # this package
└── tests/
```

Two inputs → one engine → one lattice → one query path. The Governor (`governor.py`) is the routing brain: it classifies each call as `ingest_document`, `ingest_dialogue`, or `query` and dispatches accordingly. **All three paths share the same lattice** (fact store + wiki pages + bridge blocks), and ContextHydrator pulls from all three when answering.

Key architectural decisions worth knowing before editing:

- **Wiki pages ARE dossiers.** `wiki_writer.py` writes markdown with YAML frontmatter carrying HMLR metadata (confidence, supersession chain, source turn/file IDs, last-updated). Don't add a separate dossier store — that's the antipattern this project exists to collapse.
- **Fact store stays SQL, not markdown.** Fast-changing key-value state (API keys, policy versions, counters) lives in `.hmlr/facts.db`. Wiki pages link *to* the fact store for current state rather than duplicating it. See `storage.py`.
- **Governor handles both ingest types.** On document ingest it runs Scribe (entity page updates) + FactScrubber (key-value extraction) + Summariser (writes `wiki/sources/<date>_<slug>.md`) in parallel, then appends to `log.md`. On dialogue it delegates to HMLR's `HMLRClient.chat()` and post-processes any touched entities into wiki updates at Gardener time.
- **Retrieval = LatticeCrawler (vector) + fact store (exact) + bridge block (active topic).** `index.md` is a human-browsing aid, not the retrieval path. The index.md-breaks-at-200-pages issue Karpathy's commenters flagged is handled by the vector path taking over.
- **Gardener = HMLR gardener + Karpathy lint.** One nightly (or on-trigger) process. Promotes bridge blocks to wiki pages, detects contradictions across pages via frontmatter supersession chains, resolves with a documented policy (newer source wins unless `confidence: high` in frontmatter; tie → human-review flag), regenerates `index.md`, flags orphans/stale claims.
- **Obsidian-compatible.** YAML frontmatter, `[[wikilinks]]`, plain markdown. HMLR internals live in `.hmlr/` where Obsidian ignores them.

### HMLR integration specifics

The real HMLR v0.1.2 public API (verified against [the repo](https://github.com/Sean-V-Dev/HMLR-Agentic-AI-Memory-System)):

```python
from hmlr import HMLRClient
client = HMLRClient(api_key=..., db_path=".hmlr/memory.db")
response = await client.chat(message, session_id="default_session")
# -> {"content": str, "status": str, "metadata": dict}
```

LangGraph drop-in (v0.1.2): `hmlr.integrations.langgraph` — `hmlr_memory_node`, `hmlr_chat_node`, `HMLRState`. Dossier exposes its own equivalents in `dossier.integrations.langgraph` that layer the wiki surface on top.

HMLR is **only tested with gpt-4.1-mini**. Don't switch models without re-running Hydra9 Hard Mode — the verified benchmarks (RAGAS 1.0 faithfulness, 100% context reconstruction on 21-message / 30-day isolation) are model-specific claims.

### When adding a new wiki-page type

1. Add a subdirectory under `wiki/` (e.g. `wiki/events/`).
2. Add a frontmatter schema entry in `frontmatter.py` — every new page type needs `confidence`, `sources`, `last_updated`, `supersedes` fields at minimum.
3. Teach `scribe.py` (or a new writer) how to populate it.
4. Add a lint rule in `gardener.py`: orphan detection, cross-ref coverage, stale-claim threshold.
5. Regenerate `index.md` — don't hand-edit it.

### Testing philosophy

- **Don't mock the file system in wiki_writer tests.** Use `tmp_path` fixtures. The markdown round-trip (frontmatter parse → write → reparse) is load-bearing for contradiction resolution and needs real I/O.
- **Don't mock HMLR in integration tests either** — use the `hmlr_adapter` stub (opt-in via `DOSSIER_USE_STUB=1`). It's a fake, not a mock, and mirrors the real API shape.
- **Benchmarks live under `tests/bench/` and never run by default.** The gate (`tests/bench/conftest.py`) requires both `--run-bench` *and* `OPENAI_API_KEY`. With the flag set but no key, tests fail loud with a skip reason — don't silently pass. Run RAGAS eval: `pytest tests/bench/ --run-bench -k ragas -s`. Run the Hydra9 doc-variant when implemented: `pytest tests/bench/ --run-bench -k hydra9`.
- **RAGAS is the regression detector.** `tests/bench/test_ragas_rag.py` generates a testset over [tests/bench/fixtures/raw/](dossier/tests/bench/fixtures/raw/) with `TestsetGenerator.generate_with_langchain_docs`, runs each question through `dossier.query.query()`, answers with `gpt-4.1-mini` (HMLR's tested model), and scores with `ContextRecall / ContextPrecisionWithReference / Faithfulness / AnswerRelevancy`. Metric names move around across RAGAS versions — the bench uses the v0.4.3 `ragas.metrics.collections` module (the v1.0 path). If you upgrade RAGAS, re-check `dir(ragas.metrics.collections)` before trusting the name match.

## AiGENTIS — legacy project (reference only)

Brief orientation so you don't get lost if the user asks about it:

- Next.js 14 App Router (`src/app/`), React 18, Tailwind + shadcn/ui, Zustand for state.
- React Flow canvas for visual workflow editing (`src/components/canvas/`, `src/components/nodes/`).
- Plugin system: all nodes belong to a plugin (`src/plugins/`), plugins declare canvas-specific availability and templates.
- Playwright-based browser automation service (`src/services/browser-service/`).

- Clerk auth, Stripe billing.
- Scripts:
  - `npm run dev` — Next dev server
  - `npm run build` — production build
  - `npm run test` / `test:watch` — Jest + Testing Library
  - `npm run lint`
  - `postinstall` runs `scripts/install-youtube-dl.js` and `prisma generate` (skip with `SKIP_POSTINSTALL=1`)
- Conventions are in [.windsurfrules](.windsurfrules); docs under [docs/](docs/) and [Instructions/](Instructions/).

Don't touch the AiGENTIS tree unless explicitly asked. The Dossier project is the active work.
